# 작업 규칙 (backend)

- `backend/` 폴더 안의 작업에만 적용되는 하위 규칙
- 최상위 `CLAUDE.md`의 전역 규칙과 함께 적용. 충돌하면 최상위 규칙이 우선

## 1. 작업 범위
- 서버 코드, 테스트, 패키지 설정만 다룸
- 결과물은 `backend/` 안에만 저장
- `frontend/`, `docs/` 수정이 필요하면 직접 고치지 않고 필요한 변경 내용을 사용자에게 알림
- 서버가 계산하는 규칙은 `docs/tech/tech_stack.md` 2.2에서 서버로 정한 것뿐 (4종 경로 만들기까지). 표시 순서, 추천 이유, 출발 시각, 출근 퇴근 전환은 만들지 않음

## 2. 기준 문서
| 문서 | 쓰임 |
|---|---|
| `docs/tech/api_spec.md` | 엔드포인트, 요청, 응답, 개인정보 기준 |
| `docs/tech/datasource.md` | 외부 API 항목, 호출 제한, 확인 사항 |
| `docs/tech/tech_stack.md` | 라이브러리, 폴더 구조, 캐시, 실행 방법, 환경 변수 |
| `docs/product/rules.md` | 3 ~ 7장, 10장 경로 만들기 규칙, 12장 기본값 |

- 문서와 코드가 다르면 문서를 기준으로 하고, 문서 변경이 필요하면 사용자에게 먼저 확인

## 3. 기술 규칙
- Python 3.14, `tech_stack.md` 3.1의 라이브러리만 사용. 그 외 라이브러리 추가는 사용자 확인 후 진행
- Python 문자열은 docstring을 포함해 모두 작은따옴표. `ruff check`의 `Q` 규칙으로 확인 (`tech_stack.md` 3.3)
- 응답 필드 이름은 낮은 카멜 표기. Python 코드는 밑줄 표기로 쓰고 Pydantic 모델의 별칭으로 바꿈
- 시간 길이는 초 단위 정수로 응답. 서버에서 분 단위로 바꾸지 않음
- 외부 API 호출은 httpx 비동기 호출로 하고, 서로 기다릴 필요가 없는 호출은 동시에 함
- 외부 API 장애, 사용량 초과, 시간 초과는 HTTP 오류로 끝내지 않고 `api_spec.md` 1.2의 `status`로 응답
- `rules.md` 12장 기본값은 `app/config.py` 한 곳에 상수로 모아 둠

### 3.1 경로 만들기 (`app/planner/`)
- 외부 호출 결과를 인자로 받는 순수 함수로 작성. 함수 안에서 외부 API, 캐시, 지금 시각에 접근하지 않음
- 외부 호출은 `app/clients/`, 호출 순서 조정은 `app/routers/recommend.py`에서만 함

## 4. 데이터 규칙

### 4.1 인증키
- 인증키는 환경 변수로만 읽음. 이름은 `tech_stack.md` 7장
- 카카오 REST API 키는 서버에서만 사용하고 응답, 화면, 로그에 넣지 않음
- 인증키 값을 코드, 문서, 로그, 오류 메시지에 적지 않음. 외부 호출 주소를 로그에 남길 때는 키 부분을 지움
- `.env`는 git에 올리지 않음. 새 환경 변수가 생기면 `.env.example`에 이름만 추가

### 4.2 개인정보
- `api_spec.md` 6장의 값 외에는 받지 않음
- 주소, 장소 검색어, 좌표를 파일, 데이터베이스, 로그에 쓰지 않음. 메모리 캐시(`tech_stack.md` 3.5)에만 보관 시간 동안 둠
- 로그에는 요청 주소, 응답 코드, 처리 시간, 외부 호출 결과 상태만 기록
- 쿠키, 세션, 사용자 식별 값을 만들지 않음

### 4.3 호출 수
- 카카오 대중교통, 도보, 자전거 경로는 각각 하루 무료 사용량 1,000건 (`datasource.md` 2장)
- 캐시 보관 시간(`tech_stack.md` 3.5)을 바꾸거나 한 요청의 호출 수를 늘리는 변경은 사용자 확인 후 진행

## 5. 테스트
- pytest로 작성하고 `backend/` 폴더에서 실행
- 테스트에서는 실제 외부 API를 호출하지 않음. 외부 응답은 `datasource.md`의 형식대로 만든 예시 응답으로 대신함
- `rules.md` 13장 검증 기준 중 경로 만들기에 해당하는 상황(V-1 ~ V-11, V-13, V-17)을 `planner/` 테스트로 작성
- `api_spec.md`의 엔드포인트마다 정상, `no_result`, `unavailable`, 422 응답 형식을 확인하는 테스트 작성
- 실제 외부 API 확인이 필요하면 사용자에게 알리고, 확인 결과를 `datasource.md`에 반영할지 먼저 확인
